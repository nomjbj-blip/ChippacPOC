## 3. 원인 상세

### 3.1 표시 Structure 선택

- `GdsMapForm.cs` 파일 열기 -> `map.ShowStructure(lib)` -> `GdsMapControl.ShowStructure(GdsLibrary lib)` 가 `lib.Structures[0].Name` 으로 그린다(`Controls/GdsMapControl.cs` 280행).
- 지금까지 쓴 U9 / OMM_TCB 파일은 첫 Structure 가 최상위였던 것으로 보인다. U8 은 하위 Cell 을 먼저 기록한 파일이라 드러났다(GDS 규격상 Structure 순서는 자유).
- DB 저장(`GdsMapForm_DbSave.cs`)의 `TOP_STRUCTURE`, 조회 화면의 `ShowPlacedElements(TopStructure, …)` 모두 이 값을 그대로 쓴다.

### 3.2 GPU 정점 한도 (운영 EXE 로 측정, `U8LoadProbe.ps1`)

| 단계 | 시간 | 관리 힙 |
| --- | --- | --- |
| `GdsReader.Read` (Micrometer) | 20.7 ~ 21.7초 | 818MB |
| `U8_PIC_C4` 펼치기 + GPU 버퍼 | 1.8초 | 1,733MB (+0.9GB) |
| `OMM_PFIC_PIC_PKG_A0` 펼치기 + GPU 버퍼 | 실패 | 실패 시점 3,608MB |

- 정점 구조 `Vertex` = 위치 8 + 색 16 + 선택 4 = **28바이트**. 다각형마다 채우기 삼각형 3(n-2)개 정점 + 외곽선 2n개 정점을 만들어 **목록 1개**(`_gpuVertices`)에 모은다.
- 제품 최상위 Cell 의 점 수 분포(펼친 BOUNDARY): 5점 48,272 / 9점 489,025 / 16점 64 / 33점 255,190 / 41점 489,180 / 65점 328,922.
- 필요한 정점: 약 **2억 6,284만 개 x 28바이트 = 약 7.4GB** -> 배열 1개 2GB 한도 초과(64비트 프로세스여도 동일). GPU 메모리도 감당하기 어렵다.
- DACruxV5(.NET 4.0 AnyCPU, 32비트 우선 없음)와 GdsMap(`Prefer32Bit=false`)은 64비트로 실행되므로 프로세스 전체 메모리보다 **배열 1개 한도와 정점 수**가 병목이다.
- 조회 화면(DB 기반, `ShowPlacedElements`)도 같은 `BuildGpuBuffers` 를 쓰므로 U8 을 저장해도 같은 이유로 열리지 않는다.

## 4. 설계

### D1. 최상위 Cell 자동 선택 + 선택 목록 (필수, 작음)

- `GdsLibrary` 에 최상위 Cell 계산 추가: SREF / AREF 로 한 번도 참조되지 않은 Structure. 읽기 끝(ENDLIB)에서 한 번 계산.
- 기본 선택 규칙: 최상위 Cell 중 **펼친 요소 수가 가장 많은 Cell**(빈 Cell 제외). U8 -> `OMM_PFIC_PIC_PKG_A0`. 최상위 Cell 이 1개면 그 Cell(U9 / OMM_TCB 동작 유지).
- Setup 화면 도구 막대에 [Cell] 선택 목록: 최상위 Cell 이름 + 펼친 요소 수(예 `OMM_PFIC_PIC_PKG_A0 (161만)`, `TOP (6.8만)`). 바꾸면 그 Cell 로 다시 펼친다. 하위 Cell 은 목록에 넣지 않는다(필요하면 후속).
- `ShowStructure(lib)`(첫 Structure) 는 최상위 Cell 기준으로 바꾸고, DB 저장 `TOP_STRUCTURE` 는 선택한 Cell 이름을 그대로 쓴다(조회 / 복사 / Chain 은 수정 불필요).
- 펼치기 전에 예상 정점 수를 계산해 D3 적용 전 한도를 넘으면 "표시 한도 초과(예상 n개)" 안내 후 중단(현재처럼 예외로 끝나지 않게).

### D2. 펼치기 전 Layer 선택 (권장)

- 지금은 전체 Layer 를 펼친 뒤 Layer 목록에서 숨기거나 저장 범위를 정한다(CLAUDE-021). U8 처럼 큰 파일은 펼치기 전에 **읽은 Layer 목록(요소 수 포함)** 을 보여 주고 필요한 Layer 만 펼친다.
- 효과: 고르지 않은 Layer 는 화면 항목 / 정점이 생기지 않는다. 펼친 BOUNDARY 가 많은 Layer 는 55(489,180) / 18(325,238) / 860(192,032) / 11(137,083) / 1·17(각 126,839) 순이다(Layer 별 의미는 고객 확인 필요).
- 기본값: 전체 선택(지금 동작). 요소 수가 기준(예 50만)을 넘을 때만 선택 창을 띄운다.

### D3. GPU 정점 구조 개선 (U8 표시에 필수)

| 항목 | 현재 | 변경 |
| --- | --- | --- |
| 버퍼 | 목록 1개 + VBO 1개 | **Layer 별 배열 / VBO** (배열 1개 2GB 한도와 무관하게) |
| 정점 크기 | 28바이트(위치 8 + 색 Vector4 16 + 선택 4) | **12바이트**(위치 8 + 색 RGBA8 4, 선택은 alpha 의 비트 또는 별도 작은 버퍼) |
| 채우기 | 삼각형마다 정점 3개 복사 | 다각형 점 n 개 + 인덱스 3(n-2)개(`glDrawElements`) |
| 외곽선 | 변마다 정점 2개 복사 | 같은 정점으로 `GL_LINE_LOOP`(`glMultiDrawArrays`) |

- 추정(제품 최상위 Cell 전체 Layer): 정점 5,450만 x 12B = 0.65GB + 채우기 인덱스 1.54억 x 4B = 0.62GB -> **약 1.3GB**(현재 7.4GB). 배열은 Layer 별로 나뉘어 가장 큰 Layer(55, 48.9만 개)도 1GB 미만.
- 선택 / Chain 강조 등 기존 부분 업로드(`UploadVertexRanges`, `FillVertexOffset`)는 Layer 별 오프셋으로 바꾼다. 부분 업로드 / 선택 표시 / Chain Overlay 회귀 시험 필요.

### D4. 표시용 원 단순화 (선택, D3 뒤 측정 후 결정)

- 33 / 41 / 65점 원(107만 개)을 표시할 때만 16각형으로 그린다. 선택 / 추적 / DB 저장 좌표(WorldPoints)는 원본 그대로.
- 추정: 정점 2,180만 + 인덱스 5,570만 -> 약 0.5GB. 확대 시 원 모양이 약간 각지는 차이만 있다.
- 더 큰 효과가 필요하면 반복 Cell(TSV / C4_ref / RDL_nonPCIE 각 2.7만 회) 인스턴싱(도형 1벌 + 위치 목록)을 검토한다(변경 범위 큼, 후속).

### D5. 파서 일반화 (U8 에는 불필요, 다른 고객 파일 대비, 낮은 우선)

- BOX(0x2D) 요소를 BOUNDARY 처럼 읽기, STRANS 절대 배율 / 절대 각도 비트(0x0004 / 0x0002), PATH 확장(BGNEXTN / ENDEXTN, PATHTYPE 4).
- 화면 펼치기(`FlattenStructure`)는 AREF 를 펼치지 않는다(SREF 만). DB 저장은 AREF 가 있으면 막는다. AREF 를 쓰는 파일이 오면 펼치기 추가 필요.
- 지원하지 않는 레코드를 읽었을 때 개수를 로드 결과에 표시(KLayout 과 다를 수 있음을 알림).

### D6. Label 처리 (U8 Net 분석 연결, 10/21 회의 후 확정)

- TEXTTYPE 3(핀 번호) / 4(Net 이름) 을 구분해 보관 / 표시. Chain Input 이름 자동 지정(CLAUDE-049)과 Label 검색에서 어느 TEXTTYPE 을 쓸지 선택.
- 같은 위치 같은 내용의 중복 Label 은 펼칠 때 1개로 합친다(제품 최상위 + backside_all 중복).
