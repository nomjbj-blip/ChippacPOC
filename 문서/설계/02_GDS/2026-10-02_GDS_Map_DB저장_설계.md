## 1. 목적과 범위

GDS Map Setup 화면(DMS 메뉴 `MNU_DMS_GDS_MAP_SETUP`)에서 읽은 GDS 도면을 이미 생성된 `TQP_GDS_*` 테이블에 저장한다. 저장한 데이터는 추후 별도 조회 화면에서 GDS 파일 없이 Map / Grid를 다시 그리는 데 사용한다.

| 구분 | 이번 범위 | 제외 (후속) |
| --- | --- | --- |
| 화면 | GDS Map Setup에 Device 정보 입력 / DB 저장 / 진행률 / 취소 | 조회 화면 / DB에서 Map 복원 |
| 테이블 | MAP_REV / LAYER / SOURCE_EL / PLACED_EL / IMPORT_JOB / IMPORT_BATCH | MAP_ACTIVE 지정 / Chain 6개 테이블 |
| 서버 | 기존 SEMDMS RO / Interface / BSL / DSL / Query XML 구조에 신규 클래스 추가 | 기존 함수 변경 |

Chain 저장은 READY 상태 Map을 참조해야 하므로 Map 저장이 끝난 뒤 별도 단계로 진행한다.

## 3. 전체 흐름

```text
[GDS Map Setup 화면]                         [SEMDMS Service / BSL]                 [DMSMGR]
 GDS 파일 열기 -> 화면 표시
 Factory / Device / Revision Code 입력
 [DB 저장] 클릭
   1. 파일 SHA-256 / 예상 건수 계산 (백그라운드)
   2. BeginMapImport ------------------------> REV 조회
                                               없으면 CreateMapRevision(DRAFT) 재사용
                                               IMPORT_JOB(UPLOADING) 생성 ----------> INSERT
                                    <--------- RevisionId / JobId / 완료 배치 목록
   3. LAYER 배치 (1개) ---------------------> UploadBatch ------------------------> LAYER INSERT + BATCH 기록
   4. SOURCE 배치 (N개) --------------------> UploadBatch ------------------------> SOURCE_EL INSERT + BATCH 기록
   5. PLACED 배치 (M개) --------------------> UploadBatch ------------------------> PLACED_EL INSERT + BATCH 기록
      (진행률 = 서버 확정 건수 기준)
   6. CompleteMapImport -------------------> 건수 / 좌표 수 / 누락 배치 검사
                                               JOB READY + REV READY ---------------> UPDATE
 완료 메시지 (RevisionId 표시)
 [취소] -> CancelMapImport -----------------> JOB CANCELLED (REV는 DRAFT 유지, 조회 대상 아님)
```

## 4. 서버 계약 (신규 Interface)

기존 `iGdsMapRegistration`은 변경하지 않고 `DACrux.SEMDMS.Interface/iGdsMapImport.cs`를 추가한다.

| 함수 | 입력 | 처리 / 반환 |
| --- | --- | --- |
| `BeginMapImport(GdsMapImportStartRequest)` | 개정본 헤더(기존 `GdsMapRevisionRequest` 내용) + 예상 SOURCE / PLACED / POINT 수 | 아래 재개 규칙 적용 후 `GdsMapImportStatus` 반환 |
| `UploadBatch(GdsMapImportBatch)` | JobId / StreamKind(LAYER / SOURCE / PLACED) / BatchNo / FormatVersion / PayloadSha256 / 행 배열 | 행 INSERT와 BATCH 기록. 확정된 누적 건수 반환 |
| `GetMapImportStatus(jobId)` | JobId | 상태 / 완료 배치 번호 / 누적 건수 |
| `CompleteMapImport(jobId, 최종 건수)` | JobId / 실제 SOURCE / PLACED / POINT 수 | 검증 성공 시 JOB / REV READY. 실패 시 FAILED와 사유 |
| `CancelMapImport(jobId, user)` | JobId | JOB CANCELLED |

**BeginMapImport 재개 규칙**

| 기존 REV 상태 | 같은 GDS SHA-256 | 처리 |
| --- | --- | --- |
| 없음 | - | REV(DRAFT) + JOB(UPLOADING) 생성 |
| DRAFT + JOB UPLOADING | 같음 | 기존 Job 재개. 완료 배치 목록 반환 -> 클라이언트는 해당 배치를 건너뜀 |
| DRAFT + JOB FAILED / CANCELLED | 같음 | 이번 범위에서는 거부하고 다른 Revision Code 사용 안내. (정리 / 재사용 절차는 후속) |
| READY | - | 거부 (이미 등록된 개정본) |
| 아무 상태 | 다름 | 거부 (같은 Revision Code에 다른 파일) |

**배치 행 DTO** (`[Serializable]`, BCL 형식만 사용)

| DTO | 필드 |
| --- | --- |
| `GdsLayerRow` | LayerId / ColorArgb / DisplayName |
| `GdsSourceRow` | SourceElementId / StructureName / SourceOrdinal / ElementType / LayerId / DataType / ParserDuplicate / PayloadVersion / PayloadBin(byte[]) |
| `GdsPlacedRow` | PlacedElementId / SourceElementId / LayerId / DataType / ElementType / Closed / PathWidth / PathType / MinX~MaxY / PointCount / PointsFormatVersion / PointsBin(byte[]) / Text 속성 5개 |

전송 본문으로 `GMP1` 바이너리를 쓰지 않고 행 DTO 배열을 쓴다. 이유: BSL은 .NET 4.0이라 4.8 GDS 프로젝트의 `MapPlacedBatchReader`를 참조할 수 없고, DB에는 어차피 행 단위로 넣기 때문이다. `GMP1`은 클라이언트 내부 / 파일 형식으로 유지한다.

**배치 해시:** Interface 프로젝트(4.0)에 `GdsMapBatchHash.Compute(rows)`를 두고 행 필드를 고정 순서 little-endian으로 이어 SHA-256을 계산한다. 클라이언트와 서버가 같은 코드를 사용하므로 서버가 다시 계산해 비교한다.

## 5. DB 적재 방식

### 5.1 배치 처리 순서 (BSL)

1. JOB이 UPLOADING인지, StreamKind 순서(LAYER -> SOURCE -> PLACED)를 지켰는지 확인한다.
2. 서버에서 해시를 다시 계산해 요청 해시와 비교한다.
3. `IMPORT_BATCH`에 같은 (JobId, Kind, BatchNo)가 있으면: 해시 같음 -> 이미 완료로 응답 / 해시 다름 -> 오류.
4. 행을 INSERT한다. 행 INSERT는 **같은 키가 이미 있으면 건너뛰는 형태**(`INSERT ... SELECT ... FROM DUAL WHERE NOT EXISTS`)로 만든다. 프레임워크의 트랜잭션 보장 여부와 무관하게 재전송이 안전해진다.
5. 모든 행이 끝나면 `IMPORT_BATCH` 기록을 INSERT하고 JOB 누적 건수 / UPDATE_TIME / UPDATE_USER를 갱신한다.

배치 기록은 행 INSERT 뒤 마지막에 남긴다. 중간 실패 시 배치 기록이 없으므로 클라이언트는 같은 배치를 다시 보내고, 이미 들어간 행은 4번 규칙으로 건너뛴다.

### 5.2 BLOB 저장 (1단계 검증 대상)

`POINTS_BIN` / `SOURCE_PAYLOAD_BIN`은 NOT NULL BLOB이다. 문자열만 받는 `ExecuteNonQuery(string[])` / `ExecuteMultiple(string[,])`로는 넣을 수 없다.

| 후보 | 내용 | 판단 |
| --- | --- | --- |
| A. `Execute1(sql, null, object[])` + XML `dbtype="Blob"` | 기존 프레임워크 경로. byte[]를 object로 전달 | **1순위.** 시험 DB에서 BLOB 1건 INSERT / 재조회 바이트 비교로 먼저 검증 |
| B. BSL에서 Oracle.ManagedDataAccess 직접 사용 (배열 바인딩 + OracleTransaction) | 성능 / 트랜잭션 확실 | 접속 정보를 Middleware 설정에서 꺼내야 하고 신규 표준 경로가 아님. A 실패 시 사용자 승인 후 검토 |
| C. HEXTORAW 문자열 | 문자열 경로로 가능 | RAW 2000바이트 한도(점 125개)로 큰 도형 불가 -> 제외 |

A가 한 행씩 실행이면 2,000행 배치에서 왕복 시간이 커질 수 있다. 1단계에서 100 / 2,000행 시간을 측정해 배치 크기를 정한다.

**1단계 검증 결과 (2026-10-02, 로컬 docker oracle19c DMSMGR, `Probes/GdsImportBlobProbe.ps1` PASS)**
- A 방식 동작 확인: `Execute1(object[])` + XML `dbtype="Blob"`으로 160,000바이트 POINTS_BIN을 넣고 같은 바이트로 재조회. BINARY_DOUBLE(`dbtype="Double"`) / 한글 CLOB(`dbtype="Clob"`) 값 일치. `NOT EXISTS` INSERT 재실행 시 중복 없음.
- 조건: Middleware SQL 로그(`SQLTrace`)가 모든 파라미터를 string으로 형변환해 byte[] / 숫자에서 실패한다. `TQP_GDS_PLACED_EL.xml` 등 테이블별 XML은 `logging="FALSE"`로 둔다. 레지스트리 SQLLogOnOff=On이어도 이 파일은 로그가 남지 않는다.
- 행마다 자동 Commit된다(트랜잭션 없음). 5.1절의 "행 중복 건너뛰기 + 배치 기록 마지막" 설계로 재전송 안전성을 확보한다.
- 속도: 행당 약 4.3~4.5ms (100행 427ms / 2,000행 8,952ms). 60만 도형이면 PLACED만 약 45분 예상. 배치 크기와 무관하게 행 수에 비례한다.
- 기존 BSL `CreateMapRevision`은 단위를 `ToString("R")`로 넘겨 1e-9가 `"1E-09"`가 되고 Oracle Decimal 변환에서 `FormatException`이 난다. 일반 GDS의 DB 단위(1e-9)로 개정본 생성이 실패하므로 수정 필요(기존 함수 변경 -> 사용자 승인 대상).

### 5.3 건수 / 완료 검증 (CompleteMapImport)

- DB COUNT(SOURCE_EL / PLACED_EL), SUM(POINT_COUNT)이 클라이언트 최종 값 / JOB 예상 값과 모두 같은지 확인한다.
- 각 StreamKind의 BATCH_NO가 0부터 빠짐없이 있는지 확인한다.
- 통과하면 JOB `READY`, REV `READY`로 바꾼다. 실패하면 JOB `FAILED` + 사유 반환, REV는 DRAFT로 남겨 조회 대상에서 제외한다.
- `TQP_GDS_MAP_ACTIVE`(현재 사용 개정본) 지정은 이번 범위에서 하지 않는다. 조회 화면 설계 때 같이 정한다.

## 6. 데이터 변환 규칙

### 6.1 LAYER
현재 화면의 Layer 목록 전체. `COLOR_ARGB` = 화면 Layer 색상 `ToArgb()`, `DISPLAY_NAME` = 현재 없음(NULL). PLACED FK 때문에 도형이 없는 Layer도 화면 목록에 있으면 저장한다.

### 6.2 SOURCE (원본 Grid 행)
- 정상 행: 기존 ID `<Structure>/E<순번>`, `PARSER_DUPLICATE = 0`.
- 파서 중복 제외 행: 신규 ID `<Structure>/D<순번>` (구조별 0부터), `PARSER_DUPLICATE = 1`. Placed에서 참조되지 않는다.
- SREF / AREF 행도 Grid 원본이므로 저장한다(`ELEMENT_TYPE` = SREF / AREF).
- `SOURCE_PAYLOAD_BIN` v1: Grid 재구성에 필요한 원본 값만 기록한다. 원본 좌표(로컬 X/Y double 배열), PATH 폭 / 타입, TEXT 문자열 / 속성, 참조 Structure 이름, 변환(반전 / 배율 / 각도), AREF 행 / 열. 형식 상세는 구현 1단계에서 확정하고 이 문서에 추가한다.

### 6.3 PLACED (화면 배치 도형)
- `MapPlacedElementData`(기존)를 그대로 사용한다. `POINTS_BIN` v1 = 월드 X/Y double little-endian 반복(점당 16바이트), `POINT_COUNT` = 점 수.
- `PATH_TYPE`은 PATH일 때만 값, 그 외 NULL (DDL CHECK 제약).
- `MIN_X`~`MAX_Y`는 `WorldBounds`. TEXT는 `TEXT_VALUE`(CLOB)에 문자열.

### 6.4 저장 전 차단 조건
- Map이 로드되지 않음 / 도면 읽기 중.
- AREF 원본이 있음: 현재 화면이 AREF를 펼치지 않으므로 저장하면 도형이 빠진 READY Map이 된다. 경고 후 저장 중단(지원 여부는 사용자 결정).
- ID 길이 초과(PLACED 1024바이트 / SOURCE 512자) / 좌표 없음: 기존 `CreatePersistenceData` 검사 재사용.

## 7. 화면 설계 (GDS Map Setup = GdsMapForm, DMS 호스트 모드)

- `*.Designer.cs`에 추가: Factory / Device ID / Revision Code 입력, `DB 저장` / `저장 취소` 버튼, 진행률 표시(기존 StatusStrip 활용 + ProgressBar). DMS 호스트 모드(`hostedByDms = true`)에서만 표시하고 단독 실행에서는 숨긴다.
- 기존 `Save DB` / `Load DB`(구형 GDS_ELEMENT 직접 저장)는 호스트 모드에서 이미 숨김 상태이며 변경하지 않는다.
- CREATE_USER: 우선 기존 시험 화면과 같이 `Environment.UserName`. DACrux 로그인 사용자 값을 얻는 공통 경로가 확인되면 교체한다.
- 저장 중: 파일 열기 / 레이어 변경 등 Map을 바꾸는 버튼 비활성화. 도면이 바뀌면 기존 `EnsureMapVersion`이 추출을 중단한다.
- UI 스레드: 배치 추출만 UI 스레드, 해시 계산 / 원격 호출은 `Task.Run`. 한 번에 보내는 배치는 1개(기존 설계)로 시작한다.

## 11. 2026-10-02 / Bulk 적재 방식 비교 (CLAUDE-005)

측정: 로컬 docker oracle19c DMSMGR / `Probes/GdsImportBulkProbe.ps1` PASS / 2,000행 기준.

| 방식 | 2,000행 시간 | 행당 | 비고 |
| --- | --- | --- | --- |
| Middleware `Execute1` + Blob 행 단위 | 약 7초 | 3.5ms | 큰 좌표 / 긴 TEXT 전용 경로 |
| Middleware `ExecuteTable(SQL, DataTable)` | 약 6.5~7초 | 3.3ms | 배열 바인딩이지만 byte[]를 Blob으로 바인딩 -> 행마다 임시 LOB |
| Middleware `ExecuteMultiple(string[,])` + `HEXTORAW` | **54~150ms** | **0.03~0.07ms** | 좌표 2,000바이트(125점) 이하. 값 / 바이트 / 한글 TEXT 정확. `ExecuteMultipleEx`와 같은 배열 바인딩 / 같은 속도 |
| (원인 분석용 측정) ODP 직접 배열 바인딩 Raw/LongRaw | 42ms (5점) | 0.02ms | **사용 안 함.** DB 접속은 Miracom.Middleware만 사용(사용자 지시) |
| (원인 분석용 측정) ODP 직접 + `NOT EXISTS` INSERT | 1.1~1.4초 | 0.6ms | 배열 DML에서 INSERT ... SELECT는 느림 |

**결정한 적재 규칙**
- DB 접속은 Miracom.Middleware만 사용한다(사용자 지시). 다건 저장 표준은 `ExecuteMultiple`이다.
- PLACED / SOURCE: 좌표(또는 Payload) 2,000바이트 이하이고 TEXT 4,000바이트 이하인 행은 `CREATE_PLACED_EL_MULTI`(일반 INSERT VALUES)을 `ExecuteMultiple`로 한 번에 넣는다. 나머지 행만 `Execute1` 행 단위.
- `ExecuteMultiple` 한 번의 호출은 원자적이다. 중복 키가 하나라도 섞이면 ORA-24381 / ORA-00001로 배열 전체가 롤백되고 일부 행만 남지 않는다(2026-10-02 확인). 따라서 재전송 중 이 오류가 나면 이전 전송이 이미 Commit된 것인지 해당 배치 ID 건수로 확인하고, 일부만 있으면 `NOT EXISTS` 쿼리로 나머지를 넣는다.
- 좌표 double은 모든 경로에서 `G17` 문자열 + `TO_BINARY_DOUBLE`로 넘긴다. XML `dbtype="Double"`은 15자리로 반올림되어 저장된다(0.30000000000000004 -> 0.29999999999999999 확인).
- 샘플 GDS(605,079도형 / 824만 점 / 대부분 작은 도형)라면 PLACED 적재가 약 45분에서 1분 안팎으로 줄어드는 것으로 추정한다. 실제 값은 구현 4단계에서 측정한다.
- Probe 래퍼 주의: Middleware는 호출한 메서드의 클래스를 스택에서 찾는다. 래퍼가 인라인되면 NullReference가 나므로 `NoInlining`을 붙인다(DSL은 try/catch가 있어 해당 없음).

- 비교 대상은 현재 Chain Version의 Member 도형뿐이다. 배경 도면 도형은 비교하지 않는다.

사용자 결정: 데이터 양이 많으므로 **GDS Map Setup 화면에서 Layer 필터로 그려진 항목만 DB에 저장하고 조회 / Chain에서 재활용**한다. 이 절이 7 / 18 / 20절의 "GDS 전체 저장" 설명보다 우선한다. 서버(Interface / BSL / DSL / XML)와 DB 스키마는 바꾸지 않는다.

**저장 기준 Layer**: 저장 버튼을 누른 시점에 Layer 목록에서 체크된(=화면에 그려진) Layer. 저장 시작 시 한 번 복사(스냅샷)하고, 저장 중에는 Layer 목록 조작을 막는다. 체크된 Layer가 0개면 저장하지 않는다.

| 테이블 | 저장 대상 | 비고 |
| --- | --- | --- |
| TQP_GDS_LAYER | 선택 Layer만(화면 색상 포함) | "LAYER에 있는 행 = 저장한 Layer". 제외 목록은 따로 남기지 않는다(스키마 변경 없음) |
| TQP_GDS_SOURCE_EL | BOUNDARY / PATH / TEXT 중 선택 Layer 행 + **SREF / AREF 전체** + 파서 중복 행 중 선택 Layer 행 | SREF / AREF는 GDS에 LAYER 레코드가 없어 Layer 값이 의미 없고(기본 0), 계층 구조라서 항상 저장한다. SOURCE는 LAYER에 FK가 없다 |
| TQP_GDS_PLACED_EL | 선택 Layer의 배치 도형만 | PLACED -> SOURCE / LAYER FK는 같은 Layer 조건이라 항상 만족 |

- **SOURCE_ELEMENT_ID 순번은 전체 기준을 유지한다.** 제외 행은 번호만 건너뛴다(예: `/E0`, `/E3`, `/E4`). 다시 매기면 PLACED의 SOURCE_ELEMENT_ID / 화면 Grid 순번과 어긋난다.
- 예상 건수(SOURCE / PLACED / 좌표)도 같은 조건으로 계산한다. 서버 `CompleteMapImport`는 기존처럼 DB COUNT와 비교한다.
- 확인창: 기존 데이터 확인 전에 "전체 N개 Layer 중 M개만 저장 / 제외 Layer 목록 / 제외 Layer는 조회 / Chain에서 쓸 수 없고 다시 쓰려면 삭제 후 재등록(Chain 설정도 삭제)"을 보여 주고 예 / 아니오(기본 아니오). 모두 체크된 경우에는 묻지 않는다.
- 저장 완료 메시지에 저장 Layer 수를 함께 보여 준다.
- 화면 없이 저장하는 Probe를 위해 기존 시그니처(Layer 조건 없음 = 전체)는 그대로 두고 Layer 조건 오버로드를 추가한다.
