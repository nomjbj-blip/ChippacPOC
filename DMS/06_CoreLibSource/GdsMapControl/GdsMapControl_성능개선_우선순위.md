# GdsMapControl 성능 개선 우선순위

## 1. 문서 목적

이 문서는 `NexplantQMS.GdsMap.csproj`의 GDS 파일 조회, 도형 구성, GPU 업로드, 화면 표시 속도를 개선하기 위한 작업을 우선순위별로 정리한다.

파일 선택부터 첫 화면 완료까지의 구간별 설계는 `GdsMapControl_파싱부터_첫화면까지_성능설계.md`를 참고한다.

초기 조회에 관한 사용자 측정 순위는 `FlattenStructure` 1위, `BuildGpuBuffers` 2위다. 아래 P 번호는 전체 기능별 관리 순서이며, 초기 조회 속도 개선의 실제 착수 순서는 측정 결과를 반영한 별도 설계를 따른다.

현재 소스를 기준으로 작성했으며, 일부 개선은 코드 적용 후 화면 검증을 기다리고 있다. 각 단계는 동일한 GDS 파일로 수정 전/후를 비교한 후 완료한다.

## 2. 개선 원칙

- Release 빌드로 성능을 측정한다.
- 기준 파일은 `SampleFile\OMM all layer2.gds\OMM all layer2.gds`를 사용한다.
- 한 번에 하나의 성능 구간만 수정하고 측정한다.
- Layer 색상/표시 상태, Label 좌표/표시 개수, 선택 결과는 기존과 동일해야 한다.
- 데이터 구조 변경과 렌더링 변경은 같은 단계에서 진행하지 않는다.

## 6. P1-1 / 5천만 정점 선할당 제거

### 현재 문제

`Controls/GdsMapControl.cs`의 `_gpuVertices`가 컨트롤 생성 시 5천만 개 정점 공간을 요청한다. 정점 하나는 float 7개로 구성되므로 이론상 약 1.4GB의 연속 메모리가 필요하다. 실제 데이터가 작아도 이 예약 비용이 먼저 발생한다.

`BuildGpuBuffers`는 `Clear()` 후 정점을 다시 채우므로 이 큰 Capacity가 재사용된다. `UploadAllGpuVertices` 내부의 `_gpuVertices.ToArray()`는 실제 정점 수만큼 배열을 추가로 복사한다. 따라서 선할당 제거만으로 대용량 도면의 최대 메모리 문제가 모두 해결되지는 않는다.

### 설계 범위

- 이번 단계는 CPU 정점 리스트의 초기 Capacity와 정점 생성 시 재할당만 다룬다.
- 정점 생성 순서, 각 도형의 Offset/Count, 색상, 선택 상태, `GL.BufferData` 호출 방식은 유지한다.
- `ToArray()` 제거와 GPU 부분 갱신은 별도 변경으로 분리한다. 두 변경을 함께 하면 정점 누락이나 선택 표시 오류가 생겼을 때 원인 구분이 어렵다.

### Capacity 계산 방식

`BuildGpuBuffers`가 정점을 추가하기 전에 현재 보이는 Layer와 Defect를 한 번 순회하여 필요한 정점 수를 계산한다. 실제 추가 로직과 같은 분기 조건을 사용한다.

| 도형 조건 | 예상 정점 수 |
|---|---:|
| 표시 중인 닫힌 도형 / 점 `n >= 3` | 채움 `3 x (n - 2)` + 외곽선 `2 x n` |
| 표시 중이며 위 조건에 해당하지 않는 도형 / 점 `n >= 2` | 선 `2 x (n - 1)` |
| Defect / 점 `n >= 3` | 채움 `3 x (n - 2)` |
| 숨긴 Layer 또는 위 조건을 만족하지 않는 도형 | `0` |

1. 합계는 `long`으로 계산하고, 리스트 인덱스와 GPU 업로드 byte 수의 허용 범위를 넘는지 예약 전에 검사한다.
2. `_gpuVertices`는 빈 리스트로 시작한다. 예상 정점 수가 현재 `Capacity`보다 클 때만 필요한 크기로 늘린다.
3. `Clear()` 후 기존 Capacity를 재사용하여 Layer 변경 때 반복 할당하지 않는다. 작은 파일을 다시 연 뒤 큰 Capacity가 계속 남는 문제는 재조회 메모리 측정으로 확인하고, 필요할 때만 별도 축소 정책을 설계한다.
4. 예상 정점 수와 생성 후 `Count`가 같은지 개발 중 검사한다. 서로 다르면 계산식과 실제 정점 생성 분기가 달라진 것이므로 해당 파일을 완료 처리하지 않는다.

### 적용 순서

1. P0 기준으로 컨트롤 생성 직후 메모리, 정점 생성 시간, 정점 수, 조회 중 최대 메모리를 기록한다.
2. 5천만 개 고정 Capacity만 제거하고 빈 도면/작은 도면의 시작 메모리를 확인한다.
3. 실제 도형 수를 기반으로 Capacity 사전 계산을 추가한 후 큰 도면에서 재할당과 정점 생성 시간을 비교한다.
4. 같은 도면을 다시 조회하거나 Layer를 반복 변경하여 Capacity 재사용과 메모리 유지량을 확인한다.

### 작업 내용

1. `Controls/GdsMapControl.cs`의 고정 5천만 개 Capacity를 제거한다.
2. 실제 생성 규칙을 따르는 정점 수 계산을 추가하고, 필요한 경우에만 Capacity를 늘린다.
3. 컨트롤 생성, 최초 조회, 반복 조회, Layer 변경의 메모리와 시간을 각각 측정한다.
4. `ToArray()`가 만든 추가 복사 비용은 별도로 기록하되 이번 변경에는 포함하지 않는다.

### 완료 기준

- 동일한 GDS/Layer 상태에서 예상 정점 수, 실제 `Count`, GPU에 전달되는 정점 수가 일치한다.
- 컨트롤 생성 직후 메모리가 P0보다 감소한다. 최초 조회와 반복 조회의 최대 메모리도 각각 기록한다.
- 기존에 열리던 기준 GDS에서 `OutOfMemoryException`이 새로 발생하지 않는다. `ToArray()`로 인한 대용량 한계가 남아 있으면 별도 과제로 기록한다.
- Layer 숨김/표시, 색상, 선택, Label 표시와 도형 Offset/Count가 기존과 같다.

## 7. P1-2 / 전체 GPU 버퍼 재생성 최소화

### 현재 문제

`UpdateVisibleLayer`, `VisibleAllLayer`, `SetLayerVisibility`, `SetLayerColor`는 `BuildGpuBuffers`를 호출한다. 이 함수는 현재 표시 중인 Layer의 정점을 처음부터 다시 만들고, `UpdateGpuBuffers`가 전체 배열을 GPU에 재전송한다. 마우스 선택과 선택 해제도 `UpdateGpuBuffers`에서 모든 도형의 선택 값을 다시 쓰고 전체 배열을 재전송한다.

현재는 숨긴 Layer의 `FillVertexOffset`/`LineVertexOffset`을 `-1`로 바꾸므로 체크만 해제해도 이후 Layer의 정점 위치가 달라진다. 먼저 이 위치를 안정화해야 부분 갱신이 가능하다.

### 설계 원칙

- 파일/Structure를 새로 조회할 때에만 모든 Layer와 Defect의 정점을 생성하고 전체 VBO를 업로드한다.
- 조회 시 숨긴 Layer도 정점과 Offset/Count를 만든다. 표시 여부는 `OnPaint`의 Layer 건너뛰기로만 제어한다.
- Layer 순서, Layer 안의 Item 순서, 채움 후 외곽선, 마지막 Defect 순서를 유지한다. 현재 반투명 도형의 겹침 결과가 달라지지 않아야 한다.
- 정점 위치는 다음 파일 조회 전까지 고정한다. 색상과 선택은 기존 Vertex의 값만 바꾼다. Vertex 구조와 Shader 변경은 이번 단계에서 하지 않는다.
- UI가 사용하는 공개 메서드의 호출 방식과 `Structure.Layers`에 체크 상태를 동기화하는 동작은 유지한다.

### 변경 상황별 처리

| 상황 | CPU 작업 | GPU 작업 | 다시 그리기 |
|---|---|---|---|
| 파일/Structure 새 조회 | 전체 정점 생성/Offset 기록 | `GL.BufferData` 1회 | 전체 |
| Layer 체크/미체크 | `Visible`만 변경 | 없음 | 전체 화면 다시 그림 |
| Layer 색상 변경 | 해당 Layer 정점의 채움/선 색상만 변경 | 해당 Layer 구간만 `GL.BufferSubData` | 전체 화면 다시 그림 |
| 선택/선택 해제 | 실제 변경된 Item의 `IsSelected`만 변경 | 변경된 Item 구간만 `GL.BufferSubData` | 전체 화면 다시 그림 |
| 색상 사전 일괄 변경 | 실제 RGB가 달라진 Layer만 변경 | 변경 구간만 업로드 | 전체 화면 다시 그림 |

### 정점 구간 관리

1. 전체 정점을 만들 때 모든 Layer의 Item을 현재 정렬 순서대로 기록한다. 숨긴 Layer도 같은 방식으로 처리한다.
2. `GlSceneItem`의 `FillVertexOffset/Count`와 `LineVertexOffset/Count`를 유지한다. 정점이 없는 TEXT는 Count `0`으로 처리한다.
3. 색상 변경을 위해 `GlSceneLayer`에 해당 Layer의 연속된 정점 시작 위치와 개수를 기록한다. 채움은 `ColorAlpha`, 선은 불투명 색상을 유지한다.
4. 선택 변경은 기존 정점 구간에서 `IsSelected`만 갱신한다. 선택이 유지된 숨긴 Layer는 표시를 다시 켰을 때 선택 색상이 그대로 보여야 한다.
5. 부분 업로드의 byte 위치와 길이는 `long`으로 계산하고, 실제 OpenTK 호출 형식의 허용 범위는 구현 전 확인한다. 변경 구간이 크면 고정 크기 임시 배열로 나누어 복사하고, 인접 구간은 묶어 호출 횟수를 줄인다.

### 단계별 구현 순서

1. 새 조회 시 모든 Layer의 정점을 생성하도록 변경한다. 체크 전/후 Offset이 변하지 않고 기존 화면과 같은지 확인한다.
2. Layer 체크/미체크에서 `BuildGpuBuffers`를 제거한다. `ZoomToFit`과 GDS TEXT 표시 기준은 각 TEXT의 Layer 상태를 그대로 사용한다.
3. Layer 색상 변경을 해당 Layer 구간의 CPU 정점 갱신과 부분 GPU 업로드로 바꾼다. 숨긴 상태에서 색상을 변경한 뒤 표시하는 경우도 확인한다.
4. 선택/선택 해제 경로에서 실제 바뀐 Item을 수집해 해당 구간만 갱신한다. 여러 Item을 선택하면 인접 구간을 합쳐 업로드한다.
5. 변경 구간이 대부분인 일괄 작업은 부분 업로드 호출 비용과 전체 업로드 비용을 P0 수치로 비교한 뒤 전환 기준을 정한다. 임의의 고정 비율을 먼저 넣지 않는다.

### 확인할 경계 조건

- GL 초기화 전 조회, 빈 도면, 전체 Layer 숨김, 다른 GDS 재조회에서 이전 VBO 데이터나 Offset을 참조하지 않아야 한다.
- 색상 변경 중 선택된 Item은 선택 강조가 그대로 보여야 한다. 선택을 해제하면 새 Layer 색상이 보여야 한다.
- Defect는 기존처럼 Layer 체크와 관계없이 그리며 마지막에 표시한다.
- `ColorAlpha` 속성 변경 동작은 기존 범위를 유지한다. 별도 갱신 기능이 필요하면 후속 과제로 분리한다.
- 진행률은 새 조회의 전체 버퍼 생성/업로드와 색상/선택의 부분 업로드를 구별한다. 빠른 체크 변경마다 전체 버퍼 생성 진행률을 표시하지 않는다.

### 작업 내용

1. 파일 조회 시 모든 Layer의 정점과 고정 Offset을 만든다.
2. Layer 표시/숨김은 VBO 변경 없이 `OnPaint`에서만 반영한다.

5. 투명 도형의 그림 순서와 Defect 표시 순서를 유지한다.

### 완료 기준

- Layer 체크/미체크 시 CPU 정점 생성과 GPU 업로드 호출이 모두 `0`회다.
- 단일 Layer 색상 변경과 단일 Item 선택에서는 전체 `GL.BufferData` 호출이 `0`회이고, 변경 구간에 대해서만 부분 업로드한다.
- 체크 전/후 각 Item의 Offset/Count가 동일하고, 색상 변경 후에도 확대/이동/선택 상태가 변하지 않는다.
- 전체 체크/미체크, 색상 변경, 선택/해제, 재조회 결과가 기존 화면과 일치한다.
- 같은 GDS/화면 조건에서 Layer 변경과 선택 반응 시간을 P0와 비교해 기록한다. 부분 업로드가 더 느린 경우 호출 묶음이나 전체 업로드 전환 기준을 다시 설계한다.

### 구현 현황

- 새 도면 조회 시 숨긴 Layer까지 고정 정점 위치로 구성한다.
- 체크 변경은 VBO 재생성 없이 화면만 다시 그린다.
- 색상/선택 변경은 변경된 정점 구간만 부분 업로드한다.
- Debug 빌드는 통과했다. 실제 GDS 화면 비교와 P0 대비 속도 측정은 아직 수행하지 않았다.
- P1-1의 5천만 정점 선할당과 최초 전체 업로드의 `ToArray()`는 그대로 남아 있다.

## 8. P1-3 / 화면 밖 도형 제외

### 현재 문제

`OnPaint`는 표시 Layer의 모든 `GlSceneItem`을 순회하고 항목별로 `GL.DrawArrays`를 호출한다. 화면 밖 도형도 CPU 순회와 Draw Call 비용을 사용한다.

### 작업 내용

1. 현재 화면을 World 좌표 `GBox`로 계산한다.
2. `GlSceneItem.WorldBounds`와 화면 영역이 겹치지 않으면 Draw Call을 생략한다.
3. 단순 전체 순회의 효과를 우선 측정한 후, 필요한 경우 격자 또는 Quadtree 인덱스를 적용한다.
4. Draw Call 수를 줄이는 Layer 단위 배치는 투명도/그림 순서를 검증한 후 진행한다.

### 완료 기준

- 화면에 걸친 도형이 잘리거나 사라지지 않는다.
- 확대 상태에서 Draw Call 수와 화면 표시 시간이 P0 기준보다 감소한다.
- 확대/이동 시 깜빡임이 발생하지 않는다.

## 9. P2-1 / Label 측정과 후보 처리 최적화

### 현재 문제

`DrawTextLabels`는 화면을 다시 그릴 때 GDS TEXT를 순회하고 `MeasureString`을 호출한다. 축소 상태에서도 표시 후보가 많으면 CPU 비용이 커진다.

### 대상 파일

- `Controls/GdsMapControl_Label.cs`
- `Controls/GdsMapControl.cs`

### 작업 내용

1. 문자열/폰트/DPI 기준으로 문자 크기를 캐시한다.
2. Label 삽입점과 캐시된 크기로 화면 밖 후보를 `MeasureString` 전에 제외한다.
3. 화면 안 Label만 겹침 검사한다.
4. 현재의 Center/Middle 기준점, 한쪽 이웃 간격, 화면 경계, 겹침 차단 규칙을 유지한다.
5. 사용하지 않는 Label 소유자 검색 코드는 P3-2에서 정리한다.

### 완료 기준

- 동일한 확대/이동 조건에서 Label 표시 개수와 좌표가 변하지 않는다.
- `MeasureString` 호출 횟수와 Label 처리 시간이 P0 기준보다 감소한다.

## 10. P2-2 / GDS 요소 일괄 정렬

### 현재 문제

`GdsLayerList.AddElement`와 `GlSceneLayerList.AddSceneItem`은 요소를 추가할 때마다 `BinarySearch` 후 `List.Insert`를 수행한다. 리스트 중간 삽입은 뒤쪽 요소를 계속 이동시킨다.

### 대상 파일

- `Gds/GdsLayer.cs`
- `Controls/GlSceneLayer.cs`
- `Elements/GdsElement.cs`

### 작업 내용

1. 파싱 중에는 Layer별 요소를 순서대로 추가한다.
2. Structure 종료 또는 파싱 종료 후 한 번만 정렬한다.
3. 기존 `DuplicatedItems` 판정 결과가 같은지 검증한다.
4. `GlSceneItem.CompareTo`가 선택 목록의 `BinarySearch`에 사용되므로 최종 정렬 순서를 유지한다.

### 완료 기준

- Layer/요소/중복 개수가 변하지 않는다.
- 도형 그림 순서와 선택 결과가 변하지 않는다.
- GDS 파일 읽기/Scene 구성 시간이 P0 기준보다 감소한다.

## 11. P2-3 / Scene 구성 백그라운드 처리

### 현재 문제

`GdsReader.Read`는 `Task.Run`으로 실행되지만 `ShowStructure`, `FlattenStructure`, `BuildGpuBuffers`, Grid 바인딩은 UI 스레드에서 실행된다.

### 작업 내용

1. GDS 파싱 결과를 기반으로 Scene Item과 CPU 정점을 백그라운드에서 생성한다.
2. OpenGL 컨텍스트가 필요한 VBO 생성/업로드만 UI 스레드에서 실행한다.
3. 조회 중 취소와 중복 조회 방지 토큰을 추가한다.
4. 완료된 하나의 Scene만 UI에 교체하여 부분 상태가 보이지 않게 한다.

### 완료 기준

- 파일 조회 중에도 화면 이동/취소 버튼이 반응한다.
- OpenGL 호출은 OpenGL 컨텍스트를 소유한 스레드에서만 실행한다.
- 취소된 조회의 결과가 화면에 늦게 반영되지 않는다.

## 12. P3-1 / 선택 검색 공간 인덱스

### 현재 문제

클릭 또는 드래그 선택은 표시 Layer의 모든 `GlSceneItem`을 순회한다. 도형이 많을수록 선택 시간이 증가한다.

### 작업 내용

1. P1-3의 화면 후보 검색과 공유할 수 있는 격자 인덱스를 사용한다.
2. 클릭은 마우스 주변 셀만 검색한다.
3. 드래그 선택은 선택 박스와 겹치는 셀의 항목만 검색한다.
4. 현재의 정사각형 선택 제한과 토글 선택 규칙을 유지한다.

### 완료 기준

- 클릭/드래그 선택 결과가 기존과 같다.
- 클릭 반응 시간이 P0 기준보다 감소한다.

## 13. P3-2 / Label 소유자 코드 정리

### 정리 결과

기존 도형 소유자 탐색과 Owner 관련 필드는 Label 표시 판단에 사용되지 않아 제거했다. GDS TEXT는 특정 도형의 소유 요소가 아니다.

### 작업 내용

1. 사용 여부를 참조 검색으로 다시 확인한다.
2. 사용하지 않는 Owner 검색, 거리 계산, 격자 생성 코드를 제거한다.
3. `LayerTextLabel`에서 Owner 필드와 메서드를 제거한다.

### 완료 기준

- Label 표시 개수, 좌표, 겹침 차단 결과가 변하지 않는다.
- GDS 조회 시 Owner 인덱스 생성 작업이 수행되지 않는다.

## 14. 단계별 진행 순서

```text
P0 기준값 측정
  -> P1-1 정점 메모리 개선
  -> P1-2 Layer/선택 GPU 갱신 개선
  -> P1-3 화면 밖 도형 제외
  -> P2-1 Label 최적화
  -> P2-2 요소 일괄 정렬
  -> P2-3 백그라운드 Scene 구성
  -> P3-1 선택 공간 인덱스
  -> P3-2 미사용 코드 정리
```

P1 단계는 각 항목을 별도 커밋으로 관리한다. P2/P3는 앞 단계의 측정 결과를 보고 필요성을 다시 판단한다.

## 15. 회귀 검증 목록

성능 작업을 커밋하기 전에 다음 항목을 확인한다.

- GDS 파일의 Structure/Layer/요소 개수가 변하지 않는다.
- Layer 색상과 체크/미체크 표시가 정상이다.
- 대표 GDS TEXT의 변환 좌표가 원본 삽입 좌표와 해당 Structure 변환에 일치한다.
- Label은 표시 영역이 부족하면 숨겨지고, 충분히 확대하면 표시된다.
- 영역 경계 Label도 한쪽 이웃 간격이 충분하면 표시된다.
- 확대/축소/이동 시 도형이 잘리거나 Label이 남지 않는다.
- 도형 클릭/드래그 선택 결과가 기존과 같다.
- 색상 변경 후에도 다른 Layer/확대/선택 상태가 유지된다.
- 동일 파일을 다시 열어도 Scene Item과 Label이 중복 누적되지 않는다.
