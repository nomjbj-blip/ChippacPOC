# 공통 개발 지침

확인일: 2026-10-02 / 적용 대상: Claude / Codex / 이 프로젝트의 후속 개발

## 설명과 작업 단위

- 사용자는 C# / .NET 개발자다. 한국어로 초보자도 따라갈 수 있게 설명한다.
- 코드 작성 또는 수정 시 목적 / 수정할 파일 / 코드 설명 / 실행 명령어 / 정상 실행 확인 방법 / 다음 단계 순서를 따른다.
- 수정 전에 현재 구조와 호출 관계를 확인하고 변경 계획을 설명한다. 한 번에 큰 기능 전체를 바꾸지 않는다.
- 파일 / 화면 / 클래스에는 만든 이유와 역할을, 함수에는 목적 / 역할 / 주요 처리 흐름을 주석으로 남긴다. 좌표 변환, 저장 경계, 성능 제한처럼 중요한 로직에는 이유를 적는다.
- 과장하거나 형식적인 문장을 피한다. 구분 표시는 `/`를 사용한다.

## 현재 개발 경계

아래 제한은 [2026-10-02 파일 Map 설계서](../../문서/2026-10-02_파일Map_Setup_원형생성_설계.md)의 사용자 지시를 기준으로 정리했다. 후속 사용자 지시가 범위를 바꾸면 변경 이유와 적용 범위를 기록한다.

- 기존 화면은 보존하고 새 화면 / 전용 파일로 분리한다.
- `DMS/06_CoreLibSource`는 원칙적으로 수정하지 않는다. 예외는 `06_CoreLibSource/GdsMapControl`이다. 다른 공통 컨트롤은 호출 / 상속으로 재사용한다.
- Service / RO / BSL은 기존 함수를 재사용하고 필요하면 함수를 추가한다. 기존 함수 변경은 현재 작업에 대한 명시적인 사용자 지시가 있는지 확인한다.
- 일반 화면 컨트롤 생성과 배치는 `*.Designer.cs` / `InitializeComponent`에서 관리한다. 실행 파일에는 동작과 이벤트 처리를 둔다.
- 일반 TEST / GDS 신규 화면은 `09_TEST/DACrux.TEST.ENGUI`, Defect 화면은 `02_DMS/DACrux.SEMDMS.ENGUI`를 기준으로 한다. 기존 `frmGdsMapSetup` 호스트는 SEMDMS에 있으므로 문서 기준에 맞추려고 임의 이동하지 않는다.
- GDS 서버 기능은 기존 `DACrux.SEMDMS.RO / Interface / BSL / DSL / Service`와 Oracle Query XML 구조를 따른다. 화면에서 DB로 직접 연결하는 코드를 신규 표준으로 삼지 않는다.
- `.NET Framework 4.0` DMS와 `4.8` GDS가 함께 있다. 실제 프로젝트의 대상 Framework와 참조를 확인한다. 전체 업그레이드를 임의로 진행하지 않는다.

## 다른 작업자의 변경 보존

1. 작업 전에 Git 변경 목록과 대상 파일을 읽는다. 미커밋 / untracked 소스도 현재 작업물이다.
2. [작업 현황](작업_현황.md)에 담당 도구 / 기능 ID / 파일 범위 / 시작 시각(KST)을 적는다.
3. 같은 파일을 다른 도구가 작업 중이면 그 부분을 덮어쓰지 않는다. 담당 범위를 조정하거나 겹치지 않는 작업을 진행한다.
4. 실제 편집 직전에 파일을 다시 읽는다. 문서와 코드가 다른 경우 확인한 사실을 기록하고 오래된 문서에 맞춰 복원하지 않는다.
5. `git reset --hard`, 강제 checkout, 폴더 일괄 복사로 사용자 변경을 지우지 않는다. 바이너리 / 외부 DLL / 실행 환경을 문서 작업 때문에 변경하지 않는다.

## 중요한 변경은 바로 기록

기록 대상은 기능 동작 / 화면 구성 / 좌표 규칙 / 함수와 서비스 계약 / DB 구조 / 영구 ID / 성능 처리 / 검증 결과 / 미해결 오류 / 다음 작업이다.

| 시점 | 갱신할 문서 | 남길 내용 |
| --- | --- | --- |
| 작업 시작 | 작업 현황 | 담당 / 기능 / 파일 / 상태 |
| 결정 직후 | 해당 기능 + 당일 이력 | 결정한 이유 / 이전 기준과 차이 / 근거 |
| 작은 구현 단위 완료 | 해당 기능 + 작업 현황 + 당일 이력 | 변경 파일과 함수 / 동작 / 남은 범위 |
| 검증 직후 | 해당 기능 + 당일 이력 | 실제 명령 / 결과 / 로그 위치 / 미실행 항목 |
| 오류 또는 중단 | 작업 현황 + 당일 이력 | 마지막 성공 단계 / 오류 / 재개할 첫 단계 |
| 최종 답변 전 | 관련 문서 모두 | 소스와 상태 일치 / 다음 단계 / 담당 종료 |

이력은 추가 방식으로 쓴다. 기능 문서는 현재 상태로 갱신하되 과거 결정 변경은 이력에 남긴다. 수정할 내용이 없으면 불필요한 날짜 갱신을 하지 않는다. 문서 동시 편집 시 다른 도구의 항목을 보존한다. 담당 표는 작업 조율용이며 자동 잠금 기능은 아니다.

## 확인 수준과 DB 작업

- `설계`: 문서에만 정의되어 있다.
- `소스 확인`: 파일과 호출 관계를 읽었다. 실행 성공을 뜻하지 않는다.
- `빌드 확인`: 대상 프로젝트 / 설정 / 로그가 있는 빌드 결과다.
- `Probe 확인`: 지정 EXE나 모델 API를 검사했다. 실제 사용자 화면과는 별도다.
- `화면 확인`: 실제 실행 경로 / 샘플 / 확인 동작을 기록했다.
- `DB 확인`: 대상 환경 / 쿼리 / 결과 / 저장 후 재조회까지의 확인 범위를 기록했다.

과거 문서의 통과 결과는 `과거 기록`으로 표시한다. 현재 소스로 재실행하지 않았다면 현재 검증 완료로 쓰지 않는다.

DB의 조회 / DDL / DML 범위를 구분한다. 분석만 요청된 작업에서는 DB를 변경하지 않는다. 이미 적용한 DDL / Migration은 그대로 재실행하지 않는다. 사용자 요청 범위 안에서 테스트 환경과 기존 키 / 데이터를 확인한 뒤 작업한다. 계정 비밀번호 / 접속 문자열 / 고객 원시 데이터는 공유 문서에 복사하지 않는다.
