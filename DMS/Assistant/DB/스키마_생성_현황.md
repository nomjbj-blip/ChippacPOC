# GDS / Chain DB 스키마 생성 현황

정리일: 2026-10-02 / 작성: Codex

**구분:** 아래 생성 결과는 [2026-10-01 DB 설계서의 적용 기록](../../../문서/2026-10-01_Device_Map_Chain_DB_스키마_설계.md)이다. 현재 DDL 파일은 읽었지만 DB 접속 / 실행은 하지 않았다. 현재 데이터가 비어 있다는 뜻은 아니다.

## 생성 목적과 관계

Device마다 GDS Map 개정본을 관리하고 원본 도형과 실제 배치 도형을 나눠 저장한다. Chain은 배치 도형을 참조하며 버전별 설정과 수동 편집을 보관한다.

```text
Factory / Device
  -> Map Revision -----------------> 현재 사용 Map 선택
      -> Layer
      -> Source Element -> Placed Element
      -> Import Job -> Import Batch
      -> Chain -> Chain Version
                   -> Member -> 같은 Revision의 Placed Element
                   -> Layer Filter / Layer Rule / Edit 이력
```

## 물리 테이블 13개

아래에서 REV는 MAP_REVISION_ID, CID는 CHAIN_ID, VER는 VERSION_NO의 설명용 약칭이다. 실제 SQL에는 원래 컬럼명을 사용한다.

| 테이블 | 기본 키 | 역할 / 주요 참조 |
| --- | --- | --- |
| TQP_GDS_MAP_REV | MAP_REVISION_ID | Factory / Device / Revision Code / 파일 해시 / 단위 / 상태. Factory + Device + Revision Code 중복 금지 |
| TQP_GDS_MAP_ACTIVE | FACTORY, DEVICE_ID | 현재 사용 Revision. 같은 Factory / Device의 Revision만 참조 |
| TQP_GDS_LAYER | REV, LAYER_ID | Layer 정의 / 색상 / 표시명 |
| TQP_GDS_SOURCE_EL | REV, SOURCE_ELEMENT_ID | 원본 Structure와 Element 정보 / 원본 Payload |
| TQP_GDS_PLACED_EL | REV, PLACED_ELEMENT_ID | 반복 배치를 펼친 도형 / 월드 좌표 / Bounds / PATH / TEXT. Source와 Layer 참조 |
| TQP_GDS_IMPORT_JOB | JOB_ID | 개정본의 대량 적재 작업 / 예상 및 수신 수량 / 진행 상태 |
| TQP_GDS_IMPORT_BATCH | JOB_ID, STREAM_KIND, BATCH_NO | LAYER / SOURCE / PLACED 전송 기록 / 해시 / 크기 / 확정 시각 |

| TQP_GDS_CHAIN_VER | REV, CID, VER | 이름 / 색상 / 탐색 설정 / 현재 버전 여부 / 확정 상태 |
| TQP_GDS_CHAIN_MEMBER | REV, CID, VER, PLACED_ELEMENT_ID | 최종 포함 도형 / INPUT, OUTPUT, MEMBER / 클릭 위치 |

| TQP_GDS_CHAIN_EDIT | REV, CID, VER, EDIT_SEQ | ADD / EXCLUDE / RESTORE 이력 / 일괄 편집 묶음 |

## 반드시 유지할 제약과 형식

- Map 상태: DRAFT / READY / RETIRED. 현재 Map 선택은 같은 Device의 READY Revision을 사용하도록 Service에서 검증한다.
- Import 상태: UPLOADING / VALIDATING / READY / FAILED / CANCELLED. 실패 또는 취소된 배치를 완성 Map으로 공개하지 않는다.
- Chain 상태: ACTIVE / RETIRED. Chain Version 상태: DRAFT / READY / SUPERSEDED. 현재 버전은 최대 1개다.
- Input은 정확히 1개 / Output은 최대 1개다. 최대 건수 제약뿐 아니라 필수 Input 존재는 확정 Service에서 검사해야 한다.
- 한 도형은 여러 Chain에 속할 수 있다. Member를 PLACED_ELEMENT_ID 단독 Unique로 만들지 않는다.
- 다른 Revision의 도형이 섞이지 않도록 Chain과 도형 참조에 Revision ID를 포함한다.
- Layer Rule은 FIRST_LAYER_ID <= SECOND_LAYER_ID로 순서를 정규화하고 Tolerance는 0 이상이다.
- GUID는 VARCHAR2(36 BYTE), 월드 좌표는 BINARY_DOUBLE, 좌표 배열은 BLOB이다.
- `POINTS_BIN`은 행 단위 X/Y double 배열이다. `GMP1 v2` 전송 배치 전체를 같은 형식으로 저장하지 않는다.
- CREATE_TIME / UPDATE_TIME은 DATE, 사용자 ID는 VARCHAR2(30 BYTE) 기준이다. UPDATE_TIME은 DEFAULT만으로 갱신되지 않으므로 Service가 직접 기록한다.

## 2026-10-01 적용 기록

기존 설계서에 따르면 DMSMGR에 신규 테이블 13개 / PK 13개 / FK 18개 / Unique 제약 4개 / 인덱스 23개를 생성하고 활성 / 유효 상태를 확인했다. 당시 신규 테이블은 모두 0건이었다.

감사 컬럼 변경 중 이미 NOT NULL인 컬럼에 같은 제약을 지정하여 중단되었고, 앞선 Map Revision 컬럼명 2개는 이미 변경된 상태였다. 이후 resume SQL과 사용자 ID BYTE 변경 SQL을 적용하여 마무리한 기록이 있다. 최종 감사 시각 DATE 컬럼 13개 / 사용자 30 BYTE 컬럼 11개 / 이전 `_AT`, `_BY` 이름 0개로 기록되어 있다.

이 내용은 적용 당시 기록을 전달하기 위한 것이다. 현재 상태를 확인할 때는 대상 DB를 읽기 전용으로 점검하고 별도 일자로 결과를 남긴다.

## 2026-10-02 / 키 전환: GUID -> 시퀀스 (CLAUDE-011, 최신 기준)

사용자 결정: "기존 방식과 동일하게 시퀀스 형태, 개발자가 확인 가능하도록". 기존 DMS(TQD_STEP.STEP_SEQ 등)와 같이 키 컬럼은 NUMBER, 같은 이름의 SEQUENCE(START 1 / INCREMENT 1 / CACHE 20)를 쓰고, 번호는 `SELECT_NEXT_*_SEQ`(SELECT X.NEXTVAL FROM DUAL)로 받는다.

| 기존 GUID 컬럼 (VARCHAR2(36)) | 변경 후 (NUMBER) / 시퀀스 |
| --- | --- |
| MAP_REVISION_ID | MAP_REV_SEQ / `MAP_REV_SEQ` |
| JOB_ID | IMPORT_JOB_SEQ / `IMPORT_JOB_SEQ` |
| CHAIN_ID | CHAIN_SEQ / `CHAIN_SEQ` |
| BATCH_EDIT_ID | BATCH_EDIT_SEQ / `BATCH_EDIT_SEQ` |

- 적용 DDL: [2026-10-02_tqp_gds_schema_seq.sql](../../06_CoreLibSource/GdsMapControl/Persistence/2026-10-02_tqp_gds_schema_seq.sql). 로컬 DB의 현재 정의(감사 컬럼 변경 반영 후)를 DBMS_METADATA로 추출해 키만 바꿨다. DROP 13 -> SEQUENCE 4 -> CREATE 13 -> INDEX 6. **기존 데이터를 모두 삭제하므로 시험 DB 전용.**
- 2026-10-02 로컬 docker DMSMGR 적용: 테이블 13 / PK 13 / FK 18 / UNIQUE 4 / 비활성 제약 0 / 시퀀스 4 / VARCHAR2(36) 컬럼 0. 이전 시험 데이터는 삭제됨.
- 위 "물리 테이블 13개" 표와 10/01 DDL / Migration 파일의 GUID 키 설명은 이 전환 이전 기준이다. 다른 컬럼 / 제약은 같다.
- 시퀀스는 실패한 INSERT에도 번호를 소모하므로 번호에 빈 값이 생길 수 있다(기존 STEP_SEQ와 같음).


## 2026-10-02 / 리비전 관리 제거: Factory + Device 1:1 (CLAUDE-017, 최신 기준)

사용자 결정: "리비전 관리 하지 말자. factory, 제품에 1:1로 종속", "키를 Factory + Device로 변경", "기존 데이터가 있으면 삭제 후 재등록만". **이 절이 위의 시퀀스 키(CLAUDE-011) 절보다 우선한다.**

| 테이블 | 키 / 역할 |
| --- | --- |
| TQP_GDS_MAP (신규, 이전 TQP_GDS_MAP_REV 대체) | PK FACTORY + DEVICE_ID. TOP_STRUCTURE / GDS_FILE_NAME / GDS_SHA256 / 단위 / 형식 버전 / MAP_STATUS(DRAFT / READY) / 감사 컬럼 |
| TQP_GDS_LAYER / SOURCE_EL / PLACED_EL | 키 앞부분 MAP_REV_SEQ -> FACTORY + DEVICE_ID |
| TQP_GDS_IMPORT_JOB | PK IMPORT_JOB_SEQ(시퀀스) 유지, UQ FACTORY + DEVICE_ID(Device당 1건) |
| TQP_GDS_IMPORT_BATCH | 변경 없음 (IMPORT_JOB_SEQ) |
| TQP_GDS_CHAIN / VER / MEMBER / LAYER / RULE / EDIT | 키 앞부분 MAP_REV_SEQ -> FACTORY + DEVICE_ID, CHAIN_SEQ / BATCH_EDIT_SEQ 유지 |
| 제거 | TQP_GDS_MAP_REV / TQP_GDS_MAP_ACTIVE 테이블, MAP_REV_SEQ 시퀀스, REVISION_CODE / RETIRED |

- 적용 DDL: [2026-10-02_tqp_gds_schema_device.sql](../../06_CoreLibSource/GdsMapControl/Persistence/2026-10-02_tqp_gds_schema_device.sql)(테이블 재생성, 시험 DB 전용) -> [2026-10-02_tqp_gds_fk_delete_rule.sql](../../06_CoreLibSource/GdsMapControl/Persistence/2026-10-02_tqp_gds_fk_delete_rule.sql)(FK 7개 CASCADE 제거 + 인덱스 3개, 데이터 유지). 새로 만들 때는 두 파일을 순서대로 실행한다.
- 로컬 docker DMSMGR 적용 결과: 테이블 12 / PK 12 / UNIQUE 2 / FK 17(CASCADE 10, 일반 7) / 비활성 제약 0 / 시퀀스 IMPORT_JOB_SEQ, CHAIN_SEQ, BATCH_EDIT_SEQ. 이전 데이터(개정본 9 chippac / mat 포함) 삭제됨.
- FK 삭제 규칙: CASCADE는 헤더 TQP_GDS_MAP -> LAYER / SOURCE_EL / IMPORT_JOB / CHAIN, IMPORT_JOB -> IMPORT_BATCH, CHAIN -> VER -> MEMBER / LAYER / RULE / EDIT. 큰 테이블 사이(SOURCE -> PLACED, LAYER -> PLACED, PLACED -> CHAIN_MEMBER / EDIT, LAYER -> CHAIN_LAYER / RULE)는 일반 FK. 처음 전부 CASCADE로 만들었다가 부모 행마다 내부 DELETE가 돌아 1 Device 삭제가 10분을 넘겨 바꿨다.
- 삭제 순서(BSL `GdsMapImport.DeleteMap`): CHAIN -> PLACED_EL -> SOURCE_EL -> MAP.
- 삭제 시간(로컬 docker): SQL*Plus 직접 SOURCE 60만 행 55초, Middleware 경유 20만 행 36초(행당 0.18ms) -> 샘플 1 Device(SOURCE 64만 + PLACED 60만) 약 4분 추정. 대기 대부분 `log file switch (checkpoint incomplete)`(리두 로그 200MB x 3). 운영 DB 리두 크기에 따라 달라진다.
- 기존 `TQP_GDS_MAP_REV.xml` / DSL `TQP_GDS_MAP_REV` / BSL `GdsMapRegistration` / TEST 화면 `frmGdsMapRevisionCount`(Codex 작성)는 테이블이 없어져 동작하지 않는다(소스는 남겨 둠, 삭제 여부 사용자 결정 대기).
